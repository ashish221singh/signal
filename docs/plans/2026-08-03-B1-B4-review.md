# B1–B4 Backend Plan — Cross-Review & Gap Reconciliation

> Reviews the four backend plans (B1 accounts, B2 events, B3 agentic, B4 reporting/hardening)
> **as a set**, for coherence, sequencing thrash, and holes. Each gap has a resolution;
> material ones amend the plan docs (noted inline there too).

## Verdict
The four plans are coherent and correctly ordered (tenancy → trigger model → agent surface →
reporting/deploy-readiness). The reused core loop survives intact. Ten gaps found — none force
a re-plan; most are "document the boundary" or "cap transitional work." The two that change
scope (GR-2 server-rendered auth pages, GR-5 deploy overlap) are folded into B3.

---

## Gaps & resolutions

**GR-1 — Migration freeze point.** B1/B2/B3 each *regenerate* the single `0000` migration
(fine while pre-prod/disposable). Resolution: keep rewriting `0000` through B1–B4; **freeze at
the end of B4 / first deploy.** After freeze, all schema changes are incremental migrations.
*(Add to the B4 exit: "migrations frozen; no more `0000` rewrites after this point.")*

**GR-2 — Agentic login depends on a web UI that's built last (material).** B3 device-flow needs
a browser session to approve, and signup/login is otherwise API-only — but the React auth UI is
in the frontend phase. Without a fix, the backend isn't actually *usable* end-to-end until the
frontend exists, contradicting "backend first." **Resolution: B3 ships minimal server-rendered
HTML pages** (`/signup`, `/login`, `/cli/approve`) — plain, lightly styled with `tokens.css`,
**not** the React app — so signup → login → device-approval → deploy works standalone. The React
dashboard later replaces these pages for reporting; these stay as the always-available auth
fallback. *(Folded into B3-D3/D4 + Task 5.)*

**GR-3 — Rate-limit + key-cache are per-instance / eventually-consistent.** `@fastify/rate-limit`
(in-memory) and the 60s key→account and campaign caches are per-process; multi-instance means
per-instance limits and up-to-60s revocation lag. Resolution: **accepted for launch** (single/few
instances); Redis-backed limiting + pub/sub cache invalidation are in the already-deferred
scale bucket. Documented, not built.

**GR-4 — B3 supersedes B1's session guard (not duplication).** B1 builds `sessionGuard`
(session→accountId); B3 generalizes it into `resolveAuth` (session **or** Bearer CLI token →
`{accountId, scopes}`). Resolution: expected evolution — B3 **refactors** the guard, doesn't add a
parallel one. Call it out so review doesn't flag dead code.

**GR-5 — Deploy vs the one-active-workflow-per-event rule (material).** `signal deploy` publishing
a code-managed workflow for an `event_name` that already has an *active console-managed* workflow
would violate the B2 uniqueness rule. Resolution: **deploy respects the same rule** — it does not
silently steal an event; the conflicting item fails with a clear
`event_conflict` error naming the existing workflow, and the rest of the deploy still applies
(partial success reported). *(Folded into B3-D6 + Task 7.)*

**GR-6 — The existing Android SDK goes stale after B2.** The committed `sdk-android` sends
screen/client + dwell triggers; after B2 the ingest contract is `event_name`. Resolution: **mark
`sdk-android/` deferred** (like the old prototype) — it is refit against the new contract in the
frontend phase (web-core + native shells). Nothing consumes the live API from it meanwhile.
*(Add a `sdk-android/DEFERRED.md` when B2 lands.)*

**GR-7 — CI/verify must cover the new packages.** B3 adds `@signal/mcp` and `@signal/cli`.
Resolution: extend root `pnpm verify` and the CI matrix to typecheck/lint/test both; MCP/CLI tests
run against an ephemeral API + Testcontainers Postgres. *(Add to B3 Task 11.)*

**GR-8 — Hosting (D-1) still open; needed before deploy, not before build.** B3 `verification_uri`
and B4 `PUBLIC_BASE_URL`/`CONSOLE_ORIGINS` need a real host to go live; **local dev works
throughout** (Docker Postgres/MinIO). Resolution: keep building B1–B4 locally; **decide hosting
before the first deploy** (recommendation stands: Railway/Fly + managed Postgres).

**GR-9 — Transitional rework: B1's screen model is replaced in B2.** B1 keeps the screen trigger
(eligibility must key on *something* before `event_name` exists) and account-scopes targets; B2
deletes both. Resolution: **accepted, deliberately** (the split keeps two large changes reviewable).
**Cap B1's target investment** — only scope the existing column/endpoints, add no new target
features — since B2 removes them. Net waste is small and buys a safer B1.

**GR-10 — Interim `/cli/login` (password→token) is a standing token-mint path.** Legit for CI, but
long-lived. Resolution: keep it, **rate-limited**, and **env-gate it off in production**
(`ALLOW_PASSWORD_CLI_LOGIN`, default on in dev/test, off in prod) so device-flow is the only prod
path. *(Add to B3-D4.)*

## Accepted-by-design (not gaps)
- **Eligibility contract changes twice** (B1 drops client, B2 → event): no SDK consumes it yet, so no external breakage.
- **`managed_by='code'` locks MCP/console edits**: intended — agents edit config + `deploy` for code-managed workflows; they can still freely create console-managed ones.
- **Global-unique signup email** (one owner, one account): fine until teams (deferred).
- **Deleting user-data re-opens eligibility** for that `user_id`: correct — they're forgotten.
- **seen_events on the hot path**: resolved in B3-D7 (in-memory seen-set + async first-sighting upsert; steady state hits no DB).

## Net changes folded into the plans
- **B3-D3/D4 + Task 5:** server-rendered `/signup`, `/login`, `/cli/approve` pages; `ALLOW_PASSWORD_CLI_LOGIN` prod gate.
- **B3-D6 + Task 7:** deploy honours event-uniqueness; `event_conflict` partial-success reporting.
- **B3 Task 11:** CI/verify covers `@signal/mcp` + `@signal/cli`.
- **B4 exit:** migration freeze after B4.
- **On B2 landing:** add `sdk-android/DEFERRED.md`.

## Overall sequencing (unchanged, confirmed)
B1 accounts/tenancy → B2 event re-key → B3 agentic (now self-sufficient via server-rendered auth)
→ B4 reporting/uploads/CORS/readiness/API-doc → **freeze** → frontend phase.
